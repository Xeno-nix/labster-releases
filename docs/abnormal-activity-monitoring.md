# Abnormal Activity Monitoring

Apply `Database/migrations/2026-11-22-abnormal-activity-monitoring.sql` once, after `2026-11-21-application-monitoring.sql`, before deploying the updated server. It adds `flag_for_review` (default false), `abnormal_activities`, and a single observation watermark on each unit. It does not store process snapshots. The migration matches existing ID-column collations when creating its foreign keys.

Deploy the updated agents with this server. Application registry synchronization now returns an opaque registry revision along with the same enabled process-name/ID/platform entries. Scan responses carry that revision and a completeness indicator. Agents still make no abnormal activity decisions and maintain no history. Old or stale caches cannot change activity state. A failed registry refresh keeps the last loaded cache, and reconnection/change notifications refresh it as before.

Administrators select **Flag for Review** at `/admin/applications`. Detected flagged entries appear first with a subtle amber highlight in unit details. The separate **Abnormal Activity** tab at `/unit-monitoring/activities` provides paginated Active and History views, laboratory/unit/type/date filters, and browser-local timestamps. Active means detected and not subsequently observed to end; offline units may still have unresolved records. Only `FlaggedApplication` is currently detected. Other enum values do not install resource or connection detectors.

The existing scan coordinator records a successful observation once, before completing its shared result. Processing continues if a requesting viewer closes the modal. Activity writes lock the unit row, reject older/replayed requests using server-issued request times, validate registry freshness under shared locks, and apply transitions in a transaction. A unique database constraint provides an additional safeguard against duplicate active unit/application records. Failed scans, disconnects, timeouts, uninitialized registries, and incomplete negative observations do not close activities. Positive detections from an incomplete scan may open activities.

`DetectedAt` and scan-driven `EndedAt` use server UTC observation times. The latter is when absence was observed, not the actual process exit time. Administrative changes use their configuration-change timestamp. Historical details preserve the application name at first detection. Registry deletion closes open records and explicitly detaches their application references in the same transaction; history is retained. Disabling review/monitoring closes open records. Changing a process name/platform also ends detections associated with the old identity. Renaming display text preserves the original historical description. Enabling review takes effect only for future observations and does not rescan all computers.

Admin/Faculty authorization follows existing monitoring conventions. Query services validate the actor and intersect requested filters with the non-deleted unit/laboratory source used by existing monitoring. SQL queries receive only those permitted unit IDs. Staff currently have access across laboratories; this feature adds no new permission model. Change notifications carry no activity details: open components reauthorize and query their permitted rows over their existing Blazor Server SignalR circuits. No additional hub, protocol, worker, or browser polling loop is introduced.

Retention defaults to 30 days and runs on startup and hourly through the existing `DeviceChallengeCleanup` worker, independently of challenge cleanup failures. Configure it through `Monitoring:AbnormalActivity:RetentionDays` (1–3650) or the corresponding environment variable `Monitoring__AbnormalActivity__RetentionDays`. Only rows whose **EndedAt** is older than the retention cutoff are removed. Active records are retained regardless of age.

Run the normal `CLMS.Tests` suite for lifecycle, stale/incomplete scan, access, registry flag, coordinator, and component invalidation tests. The existing `CLMS_TEST_MYSQL` / `CLMS_REGISTRY_INTEGRATION=1` opt-in enables disposable database tests covering migrations, concurrent observations, registry configuration closure, history preservation, query filtering, retention, and the unique constraint. These tests create and remove their own uniquely named databases, not the CLMS database.

If a running development server locks normal build outputs, use `-p:BaseOutputPath=<workspace>/artifacts/abnormal-activity/bin/` when building/testing. Windows native builds can be checked locally; native macOS validation still requires a Mac.
